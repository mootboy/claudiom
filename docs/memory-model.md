# Observations, reflections and source coverage

Status: planned 0.1.0 semantics; generation and storage are not implemented yet. Exact field names and wire format will be frozen in the native persistence increment.

## Observation: what the source establishes

An observation is a small, durable note grounded in identifiable Claude conversation records. It answers “What happened, was decided, was requested, or remains unresolved that a future continuation should know?”

Useful candidates:

- explicit user preferences and requirements;
- decisions and the stated reasons for them;
- constraints discovered in the project or environment;
- verified outcomes, with the checks that support them;
- unresolved problems or hypotheses, clearly labeled as unresolved.

Examples:

- Decision: “The user selected GPL-3.0-only for this project.”
- Verified outcome: “The package smoke test ran the compiled CLI without Java.”
- Unresolved finding: “The worker timed out; a provider outage is suspected but unconfirmed.”

Each example requires actual source citations when saved. They are illustrative, not memories generated by this document.

An observation is not an entire transcript summary, a copy of tool output, hidden model reasoning, or every transient action. Skip routine chatter, duplicate notes and content with no durable relevance. Never deliberately save credentials or secrets.

A cited assistant assertion proves the assertion occurred, not that its content is correct. Attribute user requests, assistant claims and tool-verified results appropriately. Keep temporal qualifiers and scope: a passing check for one revision is not proof all future revisions pass.

## Reflection: what supported observations imply

A reflection distills one or more committed observations into useful higher-level understanding. It answers “What stable constraint, pattern, relationship or lesson should we retain from these findings?”

For example:

1. Observation: users install compiled packages without build tooling.
2. Observation: the clean-consumer check runs the CLI with Node only.
3. Reflection: “Build tooling is a developer requirement, not a consumer installation requirement.”

A reflection is synthesis, not a second unsourced observation and not an account of the model's private reasoning. It references supporting observation IDs rather than pretending its conclusion came directly from a single transcript record. One explicit durable decision may be sufficient support; recurring patterns require evidence of recurrence.

Do not strengthen uncertainty during synthesis. Several repetitions of an unverified claim do not make it verified. Keep an inference labeled as an inference, and preserve relevant limitations or disagreement.

## Minimum provenance

An observation needs:

- a stable native ID and content;
- its originating Claude session;
- stream-qualified source citations identifying parent/subagent records;
- recording time and enough source context to interpret when the claim held.

A reflection needs:

- its own stable native ID and content;
- originating session and recording time;
- one or more supporting committed observation IDs.

Recall of an observation shows its citations and can expand accessible source records. Recall of a reflection shows supporting observations, which provide the route back to source. Missing source files are reported honestly; stored memory remains readable. No model credentials are required for recall.

Native locators for UUID-less records, exact fields and replay identity are persistence-contract decisions, not guessed references. The initial release organizes memory by source session; cross-session consolidation is outside its scope.

## Selection and lifecycle

Generation proposes bounded structured records. Validate identity, citation membership, support existence and configured size/item limits before saving. Semantic usefulness and faithful attribution also require prompt design and acceptance evaluation; structural validation alone cannot guarantee truth.

Do not replace the first committed definition silently. Later corrections or supersession are explicit append-only events with traceable provenance. Dropping a memory removes it from active listing but preserves historical records and source/support references for recall. Archived supporting observations must remain available to explain a reflection; a correction to its underlying facts must also be accounted for in that reflection's lifecycle.

Transcript content is untrusted source material, not instructions to the producer. Requests inside a transcript must not override producer controls, grant tools, or change provider/privacy policy.

## Coverage is not a memory

Coverage records successful processing of a bounded source range/context. A model may legitimately return no observations or reflections; commit that empty outcome and its coverage durably so a restart does not repeatedly pay to reconsider it.

Provider failure, invalid output and cancellation do not advance coverage. Commit accepted memory and associated coverage together; recover committed progress from the native log after restart. A crash before that commit can require another model call; a crash after it must not duplicate logical generation.

Observations and reflections are independently scheduled. Do not rerun reflection synthesis merely because another hook fired if the same supporting progress was already committed.
